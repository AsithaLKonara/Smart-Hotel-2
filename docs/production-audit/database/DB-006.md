# DB-006 - Distributed Locking Bypassing DB Constraints

## Status

**Resolved** (Replaced Redis lock engine with PostgreSQL Pessimistic Locking)

## Severity

P0 - Critical

---

## Category

DATABASE

---

## Description

`InventoryLockEngine.acquireHold` executes outside the Prisma transaction. If the Node process crashes after acquiring Redis lock but before DB transaction, the lock is orphaned. Fallback DB locks also fail under high concurrency.

---

## Affected Files

- lib/inventory-lock.ts
app/api/bookings/route.ts

---

## Root Cause

Race condition between Redis lock acquisition and Database transaction commit.

---

## Production Impact

- Double bookings via OTA webhooks bypassing locks.
- Artificial inventory depletion (orphaned locks).

---

## How to Reproduce

Execute `booking-concurrency-test.ts`.

---

## Fix Guide

Step 1: Move to PostgreSQL pessimistic locking (`SELECT ... FOR UPDATE`) or fix Redis lock fallback logic.
Step 2: Ensure OTA webhooks utilize the lock engine.

---

## Acceptance Criteria

- Concurrency test returns 0 double bookings.

---

## Regression Tests

- `booking-concurrency-test.ts`

---

## Priority

Sprint 1

---

## Resolution

- **Removed `InventoryLockEngine`**: Deleted `lib/inventory-lock.ts` and its associated unit tests. We no longer rely on Redis or optimistic locking `version` fields for locking rooms, removing orphaned lock vulnerability.
- **Pessimistic Locking in Booking Engine**: In `app/api/bookings/route.ts`, the room is now exclusively locked immediately inside the Prisma `$transaction` using `SELECT ... FOR UPDATE`.
- **Pessimistic Locking in OTA Webhooks**: In `lib/ota/webhook-handler.ts`, we implemented the highly-concurrent `FOR UPDATE SKIP LOCKED` postgres query pattern to find and lock available rooms instantly without deadlocking.
