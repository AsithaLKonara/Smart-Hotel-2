# DB-003 - Missing OTA Idempotency Constraints

## Status

**Resolved** (Implemented database-level compound unique constraint)

## Severity

P0 - Critical

---

## Category

DATABASE

---

## Description

`Booking.otaReference` lacks a `@@unique` constraint. Concurrent webhook deliveries from external channels can bypass application-level checks and create duplicate bookings.

---

## Affected Files

- prisma/schema.prisma (Booking model)
lib/ota/webhook-handler.ts

---

## Root Cause

Schema does not enforce compound uniqueness for third-party identifiers.

---

## Production Impact

- Duplicate bookings created in database
- Double-charging or double-reserving rooms

---

## How to Reproduce

Send two identical OTA webhooks simultaneously. Observe both creating a booking.

---

## Fix Guide

Step 1: Add `@@unique([otaReference])` or compound unique constraint to schema.
Step 2: Run Prisma migration.
Step 3: Update webhook handler to catch `PrismaClientKnownRequestError` (P2002) and treat as idempotent success.

---

## Acceptance Criteria

- Attempt duplicate insertion manually and verify Prisma throws P2002.

---

## Regression Tests

- OTA Webhook concurrency test

---

## Priority

Sprint 1

---

## Resolution

- **Database Constraint Added**: Modified `prisma/schema.prisma` to include a compound unique constraint: `@@unique([source, otaReference])`.
- **Why Compound & Nullable?**: A compound key ensures different OTAs (e.g., Expedia vs. Booking.com) don't clash on identical reference IDs. Because PostgreSQL allows multiple `NULL` values in a unique constraint, walk-in or website bookings (which lack an OTA reference) are unaffected.
- **Idempotency Implemented**: Updated `lib/ota/webhook-handler.ts` to intercept Prisma's `P2002` Unique Constraint error gracefully inside the transaction logic. If a duplicate webhook strikes concurrently, the handler acknowledges it as an idempotent success (`{ status: 'IGNORED', reason: 'DUPLICATE' }`) instead of throwing an unhandled exception or alerting the system.
