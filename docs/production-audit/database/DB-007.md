# DB-007 - Unsafe Soft Deletes vs Unique Constraints

## Status

**Resolved** (Implemented PostgreSQL Partial Indexes to ignore soft-deleted rows)

## Severity

P2 - Medium

---

## Category

DATABASE

---

## Description

`deletedAt` is not factored into unique constraints. Soft-deleting a user/booking prevents that email or code from ever being used again.

---

## Affected Files

- prisma/schema.prisma

---

## Root Cause

Prisma unique constraints apply globally across all rows, ignoring `deletedAt != null`.

---

## Production Impact

- Users cannot re-register after account deletion.
- Confirmation codes cannot be reused.

---

## How to Reproduce

Soft delete a user. Try to register a new user with the same email.

---

## Fix Guide

Step 1: Modify unique constraints to compound with `deletedAt`, or use Partial Indexes in raw SQL.

---

## Acceptance Criteria

- Successfully register a user with a soft-deleted email.

---

## Regression Tests

- User registration flows.

---

## Priority

Sprint 3

---

## Resolution

- **Schema Refactoring**: Converted strict `@unique` constraints in `prisma/schema.prisma` into `@@index` mappings for fields across multiple models (`User.email`, `Room.number`, `Payment.providerId`, `Booking.confirmationCode`, etc.) to prevent Prisma from treating soft-deleted records as duplicates.
- **Partial Indexes**: Applied native PostgreSQL partial indexes appended with `WHERE "deletedAt" IS NULL`, ensuring that exact string constraints are only enforced for active records.
- **API Realignment**: Scanned and migrated all affected usage of `prisma.model.findUnique()` to `prisma.model.findFirst({ where: { deletedAt: null } })` across 7 separate route files and integration services, perfectly bridging backwards compatibility without data refactoring or tombstoning.
